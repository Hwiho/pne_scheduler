## 1. 검토 결론과 현 상태

이 문서는 **구현 계약과 남은 인수 기록**이다. 수동 용량 입력 배치 미리보기/내보내기,
박스 편집, SQLite 보관 기록과 Windows 알림 동반 프로세스 코드는 게시됐다.
웹과 오프라인 Tk가 같은 처리를 사용한다. 배치는 셀별 **기준용량(mAh) 직접 입력**이 기본이다.
후속 U1–U3에서 공통 셀 표(복사·연번·붙여넣기·행 오류), 핵심 조건 패널과 오류 입력
복귀를 양쪽에 구현했다. 셀 원장의 영속 저장/배치 이력까지 구현한 것은 아니다.
실제 결과 파일 수입은 배치 생성의 선행조건이 아닌 선택적 후속 기능이다.
[CI 39125000686](https://github.com/Hwiho/pne_scheduler/actions/runs/39125000686)에서
Windows native와 압축 해제 배포판 검사는 통과했다. **실제 Windows 알림 표시와 Gate F
승인은 별개로 미완료**다. 중간 확인일/최종 목표 알림, 확인·연기·완료·보관/복원과 연결
표시는 구현돼 있다. 안전한 실행기 종료, 일정 수정, 백업/복원은 후속이다.
우선순위는 [v2 로드맵 R1–R7](V2_IMPROVEMENT_ROADMAP.md)을 따르고 여기서는 중복 편성하지 않는다.

| 요구 | 현재 코드 | 빠진 부분 |
|------|-----------|-----------|
| 셀별 용량 | 배치의 셀 ID/직접 기준용량을 각 `CellProfile.nominal_capacity_mAh`에 적용 | 실측 관측값·로트 연결·단계별 기준 계보는 R6 |
| 다수 파일 | `batch.py`에 셀별 직접 기준용량 입력 미리보기·배치 생성·manifest가 추가됨 | 자동 결과 파일 대조·매칭은 선택적 후속 작업 |
| DC-IR | 기본은 단일 선택 전류; 기존 RPT/campaign 복수 값 읽기는 호환성 유지 | 복수 전류를 신규 기본값으로 확대하지 않고 기존 프로젝트 보존 |
| 고온저장 | `storage_records.py`의 로컬 SQLite, 웹의 명시적 구기록 이전, `storage_companion.py`의 Windows 알림 코드 | Windows 실기기 알림·시작프로그램·절전 복귀 검증은 없음 |

핵심 원칙: **사용자가 입력한 기준용량만 전류 계산에 사용한다.** 이 값이 설계용량인지
활성화/derating 측정용량인지 프로그램이 추정하지 않는다. 값이 비었거나 잘못됐으면
배치 생성은 차단한다. 파일명·셀 구조 추정값은 출력 전류에 사용하지 않는다.
기존 v1/v2 `.schproj`의 단일 파일 출력은 같은 바이트·전류가 나오도록 유지한다.

## 2. 용량과 실험의 시간 순서

```text
셀 ID + 기준용량(mAh) 직접 입력 → 현재 레시피의 실험 단계 선택
                                → 셀별 1C/최대 전류 미리보기
                                → 셀별 독립 파일·manifest 생성
```

같은 레시피라도 각 셀의 입력·측정값·선택 정책이 다르므로 출력은 **셀별 독립 파일**이다.
단계가 바뀌어 다른 기준용량을 쓰려면 별도 레시피/배치에서 다시 입력한다. 한 파일 안에서
실험 중 새로 측정할 미래 용량으로 이후 전류를 자동 변경한다고 약속하지 않는다.

### 2.1 향후 자동 결과 수입을 선택할 경우의 데이터 모델 초안

- `CellRecord`: 불변/고유 `cell_id`, 표시명, 설계용량(mAh), 장비·채널 연결(있으면),
  측정 레코드 참조. 셀명만으로 자동 매칭하지 않는다.
- `CapacityObservation`: `cell_id`, 단계(`activation`/`derating`), 지표(`discharge_capacity_mAh`),
  값과 단위, 측정 시각, cycle/step/채널, 원본 경로·SHA-256, 수입 시각, 품질·사용자 확인
  상태를 기록한다. 활성화/derating 용량이 무엇을 뜻하는지는 실제 장비 데이터 샘플로
  확정한다. CSV/Excel/CTS 중 **실제 제공 형식**만 파서 대상으로 삼는다.
- `CapacityPolicy`: Formation=`design` 고정; Derating=`design` 또는
  `activation_discharge`; Cycle/RPT=`design` 또는 `derating_discharge`.
  모듈/실험 단계별 선택을 명시하며 셀별 예외를 검토 화면에서 표시한다.
- `ResolvedCapacity`: 선택한 기준, 셀 ID, 값(mAh), observation ID/해시, 확정 시각.
  `I_mA = C_rate × Q_basis_mAh`. CV 종료 전류도 같은 **선택된 전류 기준**을 사용한다.
  SOC/`fEndC` 용량 종료 기준은 전류 기준과 별도 정책으로 두고, 현재 미검증 필드의
  장비 사용 승인을 이 기능이 우회하지 못하게 한다.

현재 `nominal_capacity_mAh`를 바로 의미 변경하지 않는다. `.schproj/v3`를 도입할 때
v1/v2 값은 `legacy_explicit`로 이관해 **동일 수치·동일 출력**을 유지한다. 그 값을
설계용량이라고 자동 단정하지 않고 사용자에게 확인받는다. 기존
`Q_NOM_POLICY.json`의 “명시값만 writer에 사용”은 유지하고, 다중 기준 계약·테스트가
구현될 때만 정책 스키마를 함께 갱신한다.

### 2.2 선택적 자동 결과 수입을 나중에 추가한다면

1. 소량의 실제 결과 파일로 헤더, mAh/Ah, 충·방전 방향, cycle 번호, 재측정 시
   우선순위를 매핑하는 미리보기를 만든다. 원본은 수정하지 않는다. 장비 결과에
   방전용량(mAh)이 직접 있으면 해당 값을 읽어 검산하고, 전류-시간 시계열만 있으면
   선택된 **방전 구간**의 전류를 시간 적분해 `Q_mAh = ∫ I_mA dt / 3600`으로
   계산한다(전류 부호·누락 시료·불연속 시간·구간 경계 확인 필수). 두 값이 모두
   있으면 차이와 허용오차를 보여 주고, 허용오차는 실제 데이터로 정한다.
2. 매칭 실패, 중복 셀, 음수·0·비정상 값, 누락·복수 후보, 단위 미확정, 측정 시점
   역전은 차단한다. 여러 후보 중 선택은 사용자가 한다.
3. 어떤 용량을 썼는지 **셀 × 단계 × 모듈/스텝**에 표시한다. 미리보기와 실제 writer가
   동일한 `ResolvedCapacity`/`ResolvedStep`를 소비하게 하여 화면 숫자와 SCH 숫자의
   불일치를 막는다. 변경 후 기존 미리보기·승인은 무효화한다.
4. 장비/셀 전류 한도와 용량 종료값을 재검증한다. 반올림·float32 저장 오차를
   내보내기 전 미리보기에서 보여 준다. 단위 환산은 표시와 writer에 같은 함수를 쓴다.

## 3. 셀별 배치 생성

입력은 `레시피 .schproj + 셀별 기준용량(mAh) + 실험 단계 + 타깃 장비`이다.
UI는 행별 `셀 ID / 기준용량 / 실제 1C(mA) / 최대 전류 / 차단 사유`를 확인시키고,
**미리보기 → 명시적 생성** 순서로 간다. 기준용량의 출처는 자동 인증하지 않으며
manifest에 `manual_reference_unverified`로 기록한다.

- 먼저 모든 셀의 식별자·직접 입력한 기준용량·전류·장비 범위·출력 경로를 검증한다.
  한 셀이라도 차단되면 전체 배치 생성은 시작하지 않는다. 건너뛰기는 별도 사용자가
  확인한 부분 배치에서만 허용하며 누락 목록을 남긴다.
- 파일명은 정규화한 셀 ID와 단계로 결정하고 중복/경로 이탈을 차단한다. 기존 파일
  덮어쓰기 금지. 최종 폴더와 **같은 파일시스템의 형제 임시 디렉터리**에 모두
  생성·재파싱·해시·manifest 검증을 완료한 후 하나의 디렉터리 이름 변경으로
  승격한다. 실패 시 성공으로 보이는 부분 결과를 남기지 않는다.
- 셀별 manifest: 입력 셀/레시피·기준용량, 출력 파일 해시, 검증 결과, 내보내기 등급.
  실제 측정 파일 해시는 수입 기능이 추가될 때만 포함한다.
- 기존 `release.py`의 게이트를 **각 결과물**에 적용한다. 현재 웹 경로의 SCH는
  PNE02 reopen-only 후보이며 실행용이 아니다. 정확한 파일 해시와 장비에서의 재열기
  증거 없이 배치 전체를 한 번에 “실행 가능”으로 승격하지 않는다.
- 원본 SCH를 수정하는 `patch-sch` 경로를 쓸 때는 허용된 값 필드만 바꾸고 구조/스텝
  수는 고정한다. 720처럼 writer 근거가 없는 형식은 배치에서도 쓰지 않는다.

현재 API: `POST /api/plan/cellBatch`(파일 쓰기 없음),
`POST /api/export/cell-batch`(미리보기 토큰 확인 후 로컬 디스크 쓰기).
`POST /api/import/capacity-results`는 요청이 있을 때만 검토할 선택 기능이다.
프로젝트 파생·변환 API의 무상태 계약은 유지하고, 수입 저장소와 내보내기만
local-resource 경계에 둔다. `api/routes.py::export`의 빈 폴더 제약을 우회하지 않는다.

## 4. DC-IR 정책

사용자 설명대로 **DC-IR은 전류 1개를 선택하는 흐름이 기본**이다. 기존 RPT/campaign의
복수 `dcir_pulse_c_rates`는 호환성을 위해 읽고 보존하며 단일값으로 조용히 줄이지 않는다.
신규 복수 전류 기능은 요청이 있을 때만 별도 검토한다. 전류의 개수와 별개로 각 레시피의
SOC/펄스 시간/휴지·한도는 명시 입력과 실제 장비 근거가 필요하다.

DCR 저항 계산 창(`dcr_start_s`/`dcr_end_s`)은 여전히 IR/경고 수준이며,
바이너리 필드가 장비에서 검증됐다는 뜻이 아니다. 전류 개수 변경이 그 증거 수준을
올리지 않는다.

## 5. Windows 백그라운드 고온저장 알림

브라우저 `localStorage`만으로는 브라우저를 닫은 뒤 로컬 알림 작업을 신뢰성 있게
실행할 수 없다. Web Push를 선택하면 서비스 워커·권한·서버 푸시가 필요하므로,
랩 PC에서 오프라인으로 쓰는 이 제품의 첫 구현은 **로컬 Windows 동반 프로세스**로
한다. 과거 웹 전용 결정은 2026-10-18 오프라인 요구로 대체됐다. Next.js와 Tk가
같은 SQLite와 공통 서비스를 쓰며 알림은 별도 로컬 실행기가 담당한다.

아래는 **목표 계약**이며 전부 구현됐다는 뜻은 아니다. 현 구현/미완료 구분은 §1,
추가 기능의 착수·인수 순서는 v2 로드맵 R1/R2를 따른다.

1. 저장 기록을 로컬 API의 영속 저장소(예: SQLite)에 둔다. `record_id`, 셀/시료 ID,
   시작/목표 시각(UTC + 표시 시간대), 온도, 알림 설정, 확인/완료 시각, 갱신 버전을
   가진다. 고온저장 추적은 장비 온도 데이터와 자동 동기화된다는 의미가 아니다.
2. 현재 브라우저 기록은 **명시적 1회 가져오기** 화면에서 개수·중복·충돌을 확인하고
   성공 검증 전 `localStorage` 원본을 지우지 않는다. 파일 내보내기/백업·복구도 제공한다.
3. Windows 사용자 세션에서 실행되는 최소 동반 프로세스가 같은 로컬 저장소를 읽고
   목표 시각·사전 알림을 등록한다. 알림을 누르면 해당 웹 기록을 연다. 사용자가
   시작 프로그램 등록과 알림 권한/정책을 확인하게 한다.
4. PC가 꺼져 있거나 절전/로그아웃으로 예약 알림이 지나간 경우, 다음 로그인/실행
   때 overdue를 재계산하고 중복을 억제하며, 확인/연기/완료 상태를 동기화한다.
   OS 전송과 DB 기록 사이 장애 때문에 정확히 한 번 표시를 보장하지 않는다.
   Windows 예약 알림은 종료 중에도 전달될 수 있지만 배송창은 5분이므로, 이것만으로
   보장 알림이라고 표시하지 않는다. PC가 꺼져 있는 동안 즉시 알림은 불가능하다.
5. 시간대/DST, 시스템 시계 변경, 중복 프로세스, 여러 브라우저, 데이터베이스 잠금,
   종료·삭제·연기, 24시간 이상 전원 차단 후 복귀를 Windows에서 시험한다. 알림 실패는
   기록을 잃는 것과 분리해 상태 화면에 보인다.

Windows 알림 API·예약 알림 제한 근거: [Microsoft notifications overview](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/),
[scheduled app notifications](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-scheduled),
[Edge PWA push requirements](https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/how-to/push).
현재 구현은 `Shell_NotifyIconW` balloon이며 위 예약 toast API를 사용하지 않는다.
API 교체·클릭 이동·로그인 자동 시작은 R1의 별도 인수 항목이다. OS 요청 성공은
실제 화면 표시나 사용자의 확인을 뜻하지 않는다.

## 6. 순서·완료 기준

| 작업 | 순서/병렬성 | 완료 증거 |

### 미정·외부 입력

- 자동 결과 수입을 나중에 요청한다면 활성화/derating 파일 예시, “라스” 의미,
  채택할 방전 cycle 및 재시험 시 재선택 규칙.
- 기존 복수 전류 프로젝트를 변경해야 한다면 개별 검토. 기본 단일 전류 사용에는 추가 결정 불필요.
- Windows 버전/관리 정책, PC 로그인 상태·시작 프로그램 허용 여부, 알림 수신 대상과
  사전 알림 시점. 이 조건 없이 백그라운드 전달률을 보장하지 않는다.

이 입력들이 없어도 직접 기준용량 배치는 사용할 수 있다. **실제 결과 파서·채널
자동 매칭·알림 배포 방식은 추측으로 확정하지 않는다.**
